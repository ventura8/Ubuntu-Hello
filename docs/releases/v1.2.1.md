# 🚀 Ubuntu Hello v1.2.1 Release

Welcome to the **v1.2.1** release of **Ubuntu Hello**! This release fixes a fresh install of the 1.2.0 package failing to configure on a clean Ubuntu 26.04, closes a local root-execution path through the polkit-elevated Settings process, stops the PAM module from hijacking the host process's syslog identity, makes the `confirmations` config migration run for package installs (not only source installs), corrects the mode of `config.ini`, and adds the two test tiers that found all of that: a **booted-OS tier** (a clean Ubuntu, Fedora or Arch under QEMU/KVM with an emulated TPM, exercising install, PAM logins, the greeter rule, the polkit sandbox, a reboot, purge and an upgrade from the previous release) and a **recorded-footage tier** (the real recognition loop on real camera frames, with no face pixels kept). Plural-form translations are now linted and declared in every catalog.

## ✨ What's in v1.2.1

*   **📦 Fix: a fresh install on a clean Ubuntu 26.04 failed to configure.** Ubuntu's archive has no `python3-dlib`, so the package builds dlib from source at install time — and the toolchain that needs (`python3-dev`, `python3-pip`, `cmake`, `g++`) was only *Recommended*. apt does install Recommends, but it never *upgrades an already-installed package* to satisfy one: on an image whose `python3` lagged the archive by a point release, `python3-dev` (which depends on the newer `libpython3.14-dev`) was silently left out, the dlib build died on `fatal error: Python.h: No such file or directory`, dpkg stayed `half-configured`, and every login fell through to the password with `import dlib` failing. Machines that already had the headers (developer laptops) never saw it, which is why manual testing missed it. The toolchain is now a hard dependency unless the distro's dlib is installed — `python3-dlib | python3-dev`, `python3-dlib | python3-pip`, `python3-dlib | cmake`, `python3-dlib | g++` — so apt resolves it like any Depends. The Fedora and openSUSE specs gain `python3-devel` / `gcc-c++` / Pillow and the Arch `PKGBUILD` `python-pillow` / `gcc`, which the pip build needs there too. **Reproduced and verified on a clean cloud image**: the same packages install to `install ok installed`, dlib 20.0.1 builds, `/run/ubuntu-hello` is created and `sudo` runs the module.
*   **🛡️ Security fix: the elevated Settings process restored arbitrary environment variables from argv.** When Settings elevates through `pkexec`, `elevate()` forwards the desktop's display and locale variables (`DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_DATA_DIRS`, `LANG`, …) as `--env-KEY=value` arguments so *Automatic* language and theme keep working as root. On the receiving side `window.py` wrote **every** `--env-*` argument back into `os.environ` with no allowlist. The polkit policy pins only the Python interpreter and the script path (`org.freedesktop.policykit.exec.path` / `argv1`), so any further argument is caller-controlled: a local user who can satisfy the `auth_admin` prompt (a typical desktop admin, and no new prompt if a cookie for the action is still live) could run `pkexec python3 init.py --env-PATH=/tmp/evil:/usr/bin` or `--env-LD_PRELOAD=/tmp/evil.so`. The root process then spawned `ubuntu-hello list`, `sudo -u … gsettings`, `dconf` and `loginctl` by bare name, so the planted binary or preloaded library ran as root on the first Settings action. The fix: `SESSION_ENV_ALLOWLIST` is now a single module-level constant that `elevate()` iterates to forward and the restore loop consults to accept — anything not in it (`PATH`, `LD_*`, `PYTHON*`, `HOME`, …) is dropped with a stderr notice while the argument is still consumed — and, as defence in depth, a root process pins `PATH` to `ROOT_SAFE_PATH` (`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`) before any helper is spawned, which covers every bare-name `subprocess` call site in `window.py`, `tab_models.py`, `onboarding.py` and `theme_detect.py` at once. `pkexec` and sudo's `secure_path` already reset root's `PATH` to the same directories, so a normal launch behaves identically. Reported by an automated security review (Cursor); `docs/SECURITY.md` §2.2 documents the allowlist, and four unit tests cover the injected `PATH`/`LD_PRELOAD`/`LD_LIBRARY_PATH`/`PYTHONPATH`/`HOME` cases, the root `PATH` pin, the unprivileged path being left alone, and `elevate()` forwarding only allowlisted names.
*   **🪵 Fix: the PAM module hijacked the host's syslog identity.** `pam_ubuntu_hello.so` called `openlog("pam_ubuntu_hello", …)` and never `closelog()`, so every later log line of the process that loaded it — `sudo`'s own `pam_unix(sudo:auth)` lines, the display manager's — was tagged `pam_ubuntu_hello` in the journal. A small RAII scope now opens the identity for the module's own logging and closes it before returning to the caller. Verified in the booted-OS tier: `sudo`'s lines are tagged `sudo` again.
*   **⚙️ Fix: the `confirmations` migration never ran for package installs.** 1.2.0 introduced `[video] confirmations` (several frames must agree) and promised existing configs would gain the key at their own level without tightening a hand-tuned threshold. That migration lived in `install_config.py`, which only the source installer runs; the `.deb`/RPM/Arch post-install used `config_ensure.py` and never called it, so a package upgrade left the key out and the code fell back to a single frame. The migration now lives in `config_ensure.py` (`add_missing_confirmations`, `confirmations_for`), the source installer delegates to it, and `scripts/package-configure.sh` runs it (`uh_migrate_config_ini`) on every install and upgrade. Verified on a real 1.1.6 → 1.2.1 apt upgrade over a hand-edited config: edits, comments and models kept, `confirmations` added at the user's level, a threshold tightened below Secure stays on one frame.
*   **🔏 Fix: `config.ini` was installed executable** (`0755`); it is now `0644`. `docs/SECURITY.md` also described `/etc/ubuntu-hello/` as root-only (`0700`), which was never the design — the directory is `0755` with `config.ini` and the dlib data readable, and the secrets (`models/`, `keyring-keys/`, `tpm-keys/`) in `0700` subdirectories; the document now says so.
*   **🔐 Fix: on Fedora/Arch the module could break password authentication.** The PAM line inserted by authselect (Fedora) and by hand (Arch) used `[success=end default=ignore]`. `end` is a **pam-auth-update macro** — on Debian it is expanded to a numeric jump — not a token raw Linux-PAM understands; authselect writes it verbatim into `system-auth`, and Linux-PAM, seeing an unknown action, let the module's skip return (`PAM_AUTHINFO_UNAVAIL` for an SSH session, no camera, or Ubuntu Hello disabled) surface as a hard failure instead of ignoring it. The result: on a Fedora or Arch box, an SSH login or any camera-less login failed with *"Authentication service cannot retrieve authentication info"* rather than falling through to the password. The raw insertions now use the canonical `[success=done default=ignore]` (the Debian pam-config keeps the macro it owns). Found and fixed with a live before/after on a booted Fedora guest; a lint guards the token.
*   **👻 Fix: face auth spawned a GTK overlay that crashed on a headless box.** During an authentication `compare.py` started the on-screen auth overlay (`ubuntu-hello-gtk --start-auth-ui`) unconditionally, but under PAM the module hands it a minimal environment with no display — so on a server or an SSH `sudo` the overlay crashed on open and left an apport crash report on **every** attempt (the login itself still fell back to the password correctly). The overlay is now spawned only when a display is actually reachable; the notification card is the UI otherwise, exactly as the design already intended. Found by the purge scenario's crash-report check.
*   **🪟 Fix: the post-install setup wizard crashed on a headless machine.** The launcher assumed `DISPLAY=:0` when it found no Wayland socket, so installing on a server or over SSH started GTK with no display, which crashed and left an apport crash report for the user's next login. It now launches only when a Wayland socket, the installer's own `DISPLAY`, or an `/tmp/.X11-unix/X0` socket actually exists, and otherwise logs a hint to run `--force-onboarding`.
*   **🧩 Fix: the Arch PAM module failed to load — face auth was entirely broken on Arch.** The module links `libINIReader.so.0` (from `libinih`) and `libevdev`, but the Arch package listed `libinih`/`libevdev` only under `makedepends` (build time), not `depends`, so pacman never installed them on the user's system. PAM then logged *"unable to dlopen(pam_ubuntu_hello.so): libINIReader.so.0: cannot open shared object file"* and marked the module faulty — every login silently fell back to the password with face auth doing nothing. Both are now runtime dependencies. (Debian and Fedora were unaffected: their shared-library dependencies are resolved automatically.)
*   **🏗️ Fix: the Arch package could not build dlib, which then skipped the security setup.** Arch has no `python-dlib`, so the package builds it from source at install — but its dependencies listed only `gcc` and `cmake`, not **`make`**, so cmake failed with *"unable to find a build program corresponding to Unix Makefiles"* and dlib never built. Worse, that failure aborted the whole post-install under `set -e` before the PAM line and the polkit hardening drop-in were written, leaving the login stack half-configured. `make` is now an Arch dependency, and — on every format — the dlib build runs **last and non-fatally**, after PAM and polkit are wired, so a missing toolchain can never leave the security configuration unapplied (the user can install dlib later and face auth then works).
*   **🧹 Fix: `dnf remove` left the lib directory behind on Fedora.** Python writes `__pycache__/*.pyc` next to the modules at import time; those are not tracked by any package manager, so removal left them and the (otherwise empty) `/usr/lib64/ubuntu-hello` with them. The shared pre-remove step now sweeps `__pycache__` from every lib dir it might have installed into — `/usr/lib/*/…`, `/usr/lib64/…`, `/usr/lib/…` — and drops the emptied directory. The dlib pip marker's `/var/lib/ubuntu-hello` is removed the same way.
*   **🖥️ New: booted-OS test tier (`scripts/vm/`, `tests/vm/`).** Containers cannot host PAM as a login path, the polkit helper's systemd sandbox, a TPM, reboot persistence, or a package install/upgrade/remove on a real root — and every defect that only manual testing found during v1.2.0 lived in one of those layers. `scripts/vm/vm.sh` boots a clean cloud image (Ubuntu 26.04, Fedora 44 or Arch) under QEMU/KVM with a swtpm TPM 2.0, provisions two users with cloud-init (`tester` drives the run; `alice` has a password and sudo *with* a password, so the PAM stack really runs) and runs scenario scripts inside over SSH, each printing one JSON result that `tests/vm/` asserts on. Scenarios: **install** (PAM line, module, polkit drop-in with the TPM lines, tmpfiles rule, runtime dir, catalogs, dlib importable, landmark model, file modes); **config migration** across three reinstalls; **sudo through PAM** with a synthetic model (no camera fails closed to the password in under 10 s, disabled/no-model step aside, wrong password refused, the caller's `LD_PRELOAD`/`PYTHONPATH` never reach the helper, syslog identity kept); **greeter rule** — `scripts/vm/pam_probe.py` runs the real PAM stack for a `gdm-password` service with a scripted conversation and counts the prompts, proving that with `workaround = off` the module never asks for a password itself (the HARD RULE that otherwise bounces GDM's user selection), with `sudo` as the control and `workaround = input` still letting the right password through and refusing a wrong one; **polkit sandbox** — a TPM seal/unseal run under `systemd-run` with the helper unit's exact hardening fails without the drop-in and succeeds with it, `/run/ubuntu-hello` is writable and `/home` hidden but `/run/user` visible; **reboot** — a real reboot, then `/run/ubuntu-hello` recreated by tmpfiles.d, PAM intact, polkit socket up, TPM visible, password login still works; **purge** — nothing left on disk, no PAM line, no drop-in, no catalogs, no crash report from apport or systemd-coredump, login still works; **upgrade from the previous release** — 1.1.6 downloaded from GitHub, installed (its own header defect tolerated), config hand-edited, then upgraded to the packages under test. The scenarios are written once; the package manager, lib dirs, PAM include line and who wires PAM (the package on Debian/Fedora, the user on Arch) live in `scripts/vm/lib.sh`. `UH_VM_PKG_DIR` installs packages built from the working tree; on Ubuntu the PPA's published build is the alternative. CI gains a `vm` matrix job (one runner per distro, packages from the matching packaging cell) on release branches and on demand. Documented in the test-runner skill and `AGENTS.md`.
*   **🎞️ New: recorded-footage test tier (`tests/footage/`).** Every other suite mocks dlib, so the code that decides who gets in had no automated coverage; the manual-only bugs of the last releases (a Secure threshold that matched zero frames, a nod detected only in its first two seconds) all lived there. The tier replays clips recorded from the real camera through `compare.py`'s actual scan loop, the real dlib detector, landmark predictor and encoder, and the real nod rubber stamp (`UH_REAL_DLIB=1`). Seven tests: guided enrollment on real frames, the same face authenticating at Secure from a different clip, no face never authenticating, the agreeing-frames gate, a real nod passing liveness, holding still failing it fail-closed, and the Secure threshold keeping margin. **Privacy**: pixel clips are a face and never enter the repository. `deidentify.py` keeps only what the loop consumes per frame (dark flag, face rect, five landmarks, the 128-number descriptor) and the tests replay those through the same loop; the pixels were shredded. The signals are a biometric template and stay off the repository too (`tests/fixtures/footage/` is ignored); `synthesize.py` generates a random set with the measured shape (IR strobe every other frame, same-face spread 0.094, a nod as nose travel) so CI runs the tier with no real face and no dlib at all. Wired into the coverage and compat stages of `scripts/ci-docker.sh`.
*   **🌍 i18n: plural forms.** The catalog lint could not see `ngettext()` entries: an entry with `msgid_plural` never has a bare `msgstr` line, so the parser skipped it and an untranslated plural shipped in every catalog with the lint green. The lint now walks plural entries (`msgstr[0..n]`, fuzzy, header), and every catalog header carries the language's `Plural-Forms` rule (GNU gettext's tables, CLDR where gettext is silent) — without it Python's gettext falls back to the Germanic two-form rule and silently ignores a third or fourth form. The fill script writes the rule and supplies the right number of forms.
*   **🧪 Verified**: unit suite, both lints (no-suppressions, i18n), the footage tier on real and synthetic signals, and the booted-OS tier on Ubuntu 26.04, Fedora 44 and Arch in CI with packages built from this tree (a stale check name in the polkit-sandbox test, `tpm_seal` for the recorded `tpm_tools`, was corrected so the tier passes end to end).

No new config keys, strings or runtime dependencies beyond the build toolchain now being a proper dependency (Debian: `python3-dev`, `python3-pip`, `cmake`, `g++` unless `python3-dlib` is installed; Fedora/openSUSE: `python3-devel`, `gcc-c++`, Pillow; Arch: `gcc`, `python-pillow`). Desktop / greeter / wallet compatibility is unchanged.

## 📥 Installation

Download assets from the [GitHub Release](https://github.com/ventura8/ubuntu-hello/releases/tag/v1.2.1) page. Verify against `SHA256SUMS` before installing. Download this release's assets into an empty/clean directory before running these commands — the wildcards below match by filename pattern, and leftover assets from another version in the same directory can make a package manager see multiple matches (or, for the AppImage command, pass a second matched file as a stray argument).

### Method 1: Quick Install (from release tag)
Download and review [`install.sh`](https://github.com/ventura8/ubuntu-hello/blob/v1.2.1/install.sh) from the **v1.2.1** tag, then run `bash install.sh` locally.

### Method 2: PPA (Ubuntu / Linux Mint)
```bash
sudo add-apt-repository ppa:ventura8/ubuntu-hello
sudo apt update
sudo apt install ubuntu-hello
```

### Method 3: Debian `.deb` (amd64 + arm64)
```bash
sudo apt install ./ubuntu-hello_*_$(dpkg --print-architecture).deb ./ubuntu-hello-gtk_*_$(dpkg --print-architecture).deb
```

### Method 4: Fedora RPM (amd64 + arm64)
```bash
sudo dnf install ./ubuntu-hello-[0-9]*fc44*.$(uname -m).rpm ./ubuntu-hello-gtk-*fc44*.$(uname -m).rpm
```

### Method 5: openSUSE RPM (amd64 + arm64)
```bash
sudo zypper install ./ubuntu-hello-[0-9]*lp160*.$(uname -m).rpm ./ubuntu-hello-gtk-*lp160*.$(uname -m).rpm
```

### Method 6: Arch Linux (amd64 only)
```bash
sudo pacman -U ./ubuntu-hello-[0-9]*.pkg.tar.zst ./ubuntu-hello-gtk-*.pkg.tar.zst
```

### Method 7: Snap (classic, amd64 only)
```bash
sudo snap install --dangerous --classic ubuntu-hello_*_amd64.snap
sudo snap run ubuntu-hello.host-install
```

### Method 8: AppImage (installer, amd64 + arm64)
```bash
chmod +x Ubuntu-Hello-*-$(uname -m).AppImage
./Ubuntu-Hello-*-$(uname -m).AppImage --install
```

### Method 9: Flatpak (installer, amd64 only)
```bash
flatpak install --user ./com.github.ventura8.UbuntuHello-*.flatpak && \
    flatpak run --command=ubuntu-hello-host-install com.github.ventura8.UbuntuHello
```
Approve the polkit prompt on the host-install step to install PAM and system files.

## 📋 Changelog (v1.2.1)

Fedora/openSUSE specs: `python3-devel`, `gcc-c++`, Pillow; Arch: `gcc`, `python-pillow`.
*   **Security (Settings)**: `ubuntu-hello-gtk/src/window.py` restores only `SESSION_ENV_ALLOWLIST` from `--env-*` argv (the same set `elevate()` forwards) and pins `PATH` to `ROOT_SAFE_PATH` when running as root; previously any `--env-KEY=value` reached `os.environ` and the polkit-elevated process PATH-resolved `ubuntu-hello`/`sudo`/`gsettings`/`loginctl`, allowing a local `auth_admin`-capable user root code execution. `docs/SECURITY.md` §2.2; tests in `tests/test_window_unit.py`.
*   **Fix (PAM)**: `openlog()` identity scoped with `closelog()` (`SyslogIdentityScope`); the host process's own journal lines are no longer tagged `pam_ubuntu_hello`.
*   **Fix (config)**: the `confirmations` migration moved to `config_ensure.py` and run by `package-configure.sh` (`uh_migrate_config_ini`), so package upgrades get the key at the user's level; `install_config.py` delegates. `config.ini` installed `0644`.
*   **Docs (security)**: `/etc/ubuntu-hello/` ACL description corrected (0755 directory, 0700 secret subdirectories).
*   **Fix (PAM, Fedora/Arch)**: authselect/Arch raw PAM line uses `[success=done default=ignore]`; `success=end` is a Debian-only pam-auth-update macro that Linux-PAM treated as a failure, surfacing the module's skip return and breaking password auth for SSH/camera-less logins.
